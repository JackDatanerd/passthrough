1. WHAT WAS BUILT
--------------------------------------------------------------------------------
A. Expert identity and sessions. Separate identity (expert_accounts, from 0124; nothing added to main users). Separate secret
   (EXPERT_REALM_SECRET) and audience ("expert-realm"). One cookie, "__Host-pt_xr": HttpOnly, Secure, SameSite=Strict, Path=/, no Domain.
   Server-side session rows: 8 hours idle, 7 days absolute (both read from settings: system_state key 'expert_realm', clamped; defaults in
   src/lib/expertRealm/config.js). Authenticator two-factor (enrol, challenge), ten single-use recovery codes (keyed hashes only), lockout
   (5 failures, 15 minutes, applied to password, code and recovery attempts), per-IP and per-session rate limits, step-up (fresh password lifts
   a session for 10 minutes), password reset by a one-time emailed link (token in the URL fragment, hash stored), change password, revoke all
   sessions (rows ended and token_version moved), session list. Roles: expert, grader, expert_admin, expert_support. Staff accounts are made by
   hand: scripts/expert-staff-account.cjs + docs/experts/phase2a/staff-accounts.md.
B. Permission matrix: src/lib/expertRealm/permissions.js, one table. Every realm route is declared through define() with a policy (a matrix
   action, or public / pending / session) or it cannot be mounted. Job content: the API checks the job is currently assigned to that expert,
   then the existing database function human_job_expert_read checks again and logs.
C. Audit: every sign-in, second-factor failure, denied attempt, job read, assignment and refund writes to expert_audit_log (the 0124 table). A
   filter drops keys that could carry content. Job-content reads and refund requests FAIL CLOSED if the audit write fails.
D. Job engine: ONE state machine. JS half: src/lib/expertRealm/stateMachine.js (58 transitions, who may trigger each). Database half: table
   job_transition_rules + function human_job_transition (migration 0127). A test fails if the two tables ever differ. The function checks the
   rule, the actor, who owns what, the version (compare-and-set), applies side effects, writes the event, records the idempotency key, and sets
   or clears the next action, all in one transaction. Events are the history; clocks are derived from events (src/lib/expertRealm/clock.js) with
   explicit pause intervals (table job_pauses); next actions live in job_next_actions. Phase 1 pilot data is copied into the new tables by a
   reversible backfill (rows marked source = 'phase1_backfill').
E. Bridge (src/services/expertBridge.service.js): refundHumanOrder, readHumanOrderPayment, createJobFromPayment. Server to server, logged in
   expert_bridge_calls, idempotent by (function, key), human orders only. The refund goes through the existing queueRefund.
F. Admin console API (/api/expert-admin): job board with timeline, assign, reassign, expert directory, refund (step-up, reason, request key),
   audit viewer. Support role limited to board and timeline. Screens: frontend/src/experts/pages/Admin.jsx.
G. Expert site: its own build (frontend/experts.html, vite.experts.config.js, npm run build:experts -> frontend/dist-experts), own headers and
   redirects (frontend/public-experts), sign-in, two-factor enrol and challenge, recovery codes (shown once), empty Desk, settings with the
   session list, reset flow. Colours and type from product spec 21.3, on the shared components.
H. Client order tracker: frontend/src/components/human/OrderTracker.jsx + frontend/src/lib/orderTracker.js, shown on the customer's order page.
I. Deployment checklist: docs/experts/phase2a/deployment-checklist.md.

6. DECISIONS I MADE (confirm or change)
--------------------------------------------------------------------------------
 a) Cookie scope. The main app uses Bearer tokens, so "a cookie scoped to the expert site only" needed a design: the Worker is also routed at
    experts.usepassthrough.com/api/*, the realm answers only on that host, the cookie is host-only (__Host-). No CORS, no cross-site use.
    UNVERIFIED: that a Worker route wins over the Pages custom domain on that path (checklist step 5 tells you how to check).
 b) Third secret. EXPERT_REALM_SECRET is new and must differ from JWT_SECRET and the Phase 1 EXPERT_JWT_SECRET.
 c) Mount paths /api/expert-realm and /api/expert-admin (Phase 1 owns /api/expert) and a new flag EXPERT_REALM_ENABLED.
 d) Transitions not in the spec's table, added so F can work: reassign (claimed / in_progress / waiting_customer -> claimed, operator only);
    unassign; payment_reversed (offered / open -> cancelled); revision -> in_review on submit_review (Phase 1 did this); dispute from every
    working state and from accepted; refund from every carrying state and from disputed. Not defined, so NOT built: how a dispute is resolved
    back to another state (spec 6: "an operator rules"); a grader as its own actor kind (graders act as 'expert' in events).
 e) Support can read the job board and timelines; the expert directory and the audit viewer are admin-only. The spec's table does not say.
 f) The admin job view and the expert brief show METADATA only (states, times, first name and initial). Masked job content for admin/support
    ("view full: masked") comes with the workbench. The expert brief route returns the posting with the company masked, as Phase 1 does.
 g) The Phase 1 pilot jobs' deadline and pause arithmetic is mirrored exactly (both deadlines move back by the time paused).

7. KNOWN GAPS
--------------------------------------------------------------------------------
 1. Phase 1's database functions (human_job_assign, accept, reverse, deliver, ask, ...) and humanSettle / humanSweep still write job state
    themselves. Only the realm's callers (console assign / reassign, the bridge) use human_job_transition. So "every caller uses one state
    machine" is true for the new code and NOT yet for Phase 1. A test pins that nothing new writes state elsewhere. Moving Phase 1 over means
    editing its files; it needs your approval. Until then job_pauses / job_next_actions can disagree with a job that Phase 1 moved
    (the console shows a warning when the stored paused time does not match the events).
 2. The refund bridge queues the refund; the JOB moves to refunded when the refund completes through the existing payment flow (Phase 1's
    reversal), not through the engine. The engine's 'refund' transition exists and is tested but has no caller yet.
 3. createJobFromPayment exists and is tested, but the live payment-confirmed path still calls Phase 1's human_job_confirm_payment (humanSettle).
    Rewiring it edits an existing file.
 4. No expert tier or grade exists in the data yet, so the tracker shows first name and initial but no tier (it shows one as soon as the API
    sends expertTier).
 5. "Earnings frozen on dispute": the engine records the dispute but does not freeze earnings; the ledger is Phase 5.
 6. The pending-session lifetime (10 minutes), step-up (10 minutes), reset link (30 minutes), lockout (5 / 15 minutes) and recovery-code count (10)
    are settings with clamps, but there is no screen to change them: edit system_state 'expert_realm'.
 7. The rate limiters fail open if the limiter backend errors (as every limiter in this app does). Lockout is stored in the database and does not.
 8. Grader and expert_support have no routes of their own yet (the grader queue and macros are later phases); they can sign in and see Settings.
 9. Two-factor reset for a lost phone with no recovery codes is a SQL procedure (staff-accounts.md), not a console action.
 10. The admin console has no pagination on the board (limit 100) or directory (200).
 11. A Worker route and a Pages custom domain on one hostname, the main middleware under the new host, DNS, email, a real browser and phone, live
    database, real Paystack: none of these could be exercised from here.
 12. Phase 1 pilot gate not recorded; pilot expert count unknown.
 13. Passwords: 12-character minimum plus the breached-password check (fails open like the main app's); no composition rules.
