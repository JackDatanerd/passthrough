# Passthrough Experts, Phase 2A: security note (one page)

**How the realms are separated.** The expert realm is a different identity store, token, secret, cookie and host from the main app.
- *Identity:* expert, grader, expert_admin and expert_support accounts live in `expert_accounts`. Nothing is added to the main `users` roles, and no main admin route can be reached with a realm credential.
- *Token and secret:* the realm's cookie holds a token signed with `EXPERT_REALM_SECRET`, audience `expert-realm`. The realm refuses to run if that secret is missing, under 32 characters, or equal to `JWT_SECRET` or the Phase 1 `EXPERT_JWT_SECRET`.
- *Transport:* the credential is **only** a cookie (`__Host-pt_xr`, HttpOnly, Secure, SameSite=Strict, no Domain). The realm never reads an `Authorization` header and the main app never reads cookies, so a token of either kind is inert in the other place.
- *Host:* the API is reached for the realm only through `experts.usepassthrough.com/api/*`. Realm routes answer 404 on any other host, so the cookie is first-party to the expert site and no other site can send it. State-changing requests must also carry that site as `Origin`.
- *Server-side state:* every session is a row (8 hours idle, 7 days absolute, both from settings). A session ends if its row is revoked, the account is disabled or loses all roles, or the account's `token_version` moves ("revoke all sessions", password change or reset).
- *Second factor:* required before any route works but sign-in. Authenticator app, replay-proof, five failures lock the account for 15 minutes; ten single-use recovery codes stored only as keyed hashes.

**What a stolen expert token can and cannot reach.** *Can:* what that one account's roles allow in the realm, for as long as the session lives: an expert reads the brief (company masked) of jobs currently assigned to them and their desk; support reads the job board and timelines; an admin additionally assigns, reads the directory and audit log, and may request a refund. Money, unmasking and settings routes also need a password re-entered in the last 10 minutes, which a cookie alone does not give. *Cannot:* sign in again without the password and the phone; touch any main-app route (user, partner, payment or admin) with it; read another expert's job (API check, then the database function, then an audit row for the attempt); refund anything that is not a human order; or survive "sign out everywhere", a password change, or the account being disabled. It is not readable by page scripts (HttpOnly) and is not sent from any other site.

**What is enforced where.** One permission matrix in code (`src/lib/expertRealm/permissions.js`), used by every realm route; every route is registered with a policy or it cannot be mounted. One state machine (`stateMachine.js` and the database function `human_job_transition`, kept equal by a test). Money moves only on defined transitions and is keyed so a repeat does nothing. Audit rows are written for sign-in, second-factor failures, every denied attempt, job reads, assignments and refunds; the log never holds resume text, contact details, names, tokens or secrets (a filter drops them), and job content or money actions fail closed if the audit write fails.

**What I did not test.** A real browser and phone (cookie behaviour on the live host, authenticator apps, the QR link); the deployed Worker route on `experts.usepassthrough.com` and that the main API's own middleware accepts that host; email delivery and the sender's SPF/DKIM/DMARC; the live database (everything ran on PGlite and in-memory fakes); real Paystack refunds; load and timing (the 200-experts-at-once claim race is Phase 3, not here); concurrent requests from two real sessions; and the main app's existing middleware under the new host. The cross-realm test enumerates every route the app mounts, with an in-memory database, so a route that behaves differently with real data is not covered.
